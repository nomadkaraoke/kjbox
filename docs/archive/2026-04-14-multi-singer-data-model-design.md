# Multi-Singer Data Model + Pill Input UI — Design Spec

**Date:** 2026-04-14
**Phase:** 1 of 2 (Phase 2: Singer Stats Panel with actions + undo/redo)
**Scope:** Structured multi-singer tracking, pill-based input UI, updated songs-sung counting

## Summary

Today the rotation treats singer names as free-text strings. Multi-person entries like "Phil & Anya" are stored verbatim and counted as a single identity, meaning neither Phil nor Anya gets individual credit toward their songs-sung count. This phase introduces structured multi-singer support so the system properly tracks each individual across all their entries.

## Data Model

### New column

Add `singers_json TEXT DEFAULT NULL` to `rotation_entries` via the existing schema migration pattern in `rotation_store.py`.

Contains a JSON array of individual singer names:
- Duet: `'["Phil", "Anya"]'`
- Solo: `'["Sarah"]'`
- Legacy/null: treated as single identity using the `singer` column

### The `singer` column stays

The `singer` column remains as the human-readable display string. For multi-singer entries it is auto-generated by joining the JSON array with " & " (e.g., `"Phil & Anya"`). For single-singer entries, `singer` is the name and `singers_json` is `'["Sarah"]'`.

### Backward compatibility

Lazy migration: existing entries keep `singers_json = null`. When null, the system falls back to treating the `singer` text as a single identity (current behavior). No auto-migration, no risk of mis-splitting artist names like "Simon & Garfunkel". Legacy entries cycle out naturally as the night progresses.

### Name matching

Store as-entered, match case-insensitive. Trim whitespace on entry. This matches the existing `singer` column behavior. No title-case normalization.

### Undo/redo

No changes needed. Snapshots already capture full row dicts via `_row_to_dict()`. The new `singers_json` column is included automatically. `restore_entries()` needs the column added to its INSERT statement.

## Backend Changes

### Schema migration (`rotation_store.py`)

Add to the existing `migrations` list in `init_schema()`:
```python
("singers_json", "TEXT DEFAULT NULL"),
```

### Modified store methods

**`add_entry()`** — accepts optional `singers` list parameter. If provided:
- Stores `json.dumps(singers)` in `singers_json`
- Auto-generates `singer` display string by joining with " & "

If not provided, `singers_json` stays null (backward compat).

**`update_entry()`** — also accepts optional `singers` list. Same logic: updates `singers_json` and regenerates `singer`.

**`get_songs_sung_counts()`** — changes from pure SQL GROUP BY to a Python loop:
1. Fetch all Done entries: `SELECT singer, singers_json FROM rotation_entries WHERE LOWER(status) = 'done'`
2. For each entry: if `singers_json` is not null, parse JSON array and credit each individual name (lowercased); otherwise credit the `singer` string (lowercased) as-is
3. Return the same `{lowercase_name: count}` dict

Performance: dozens of entries per night, negligible overhead.

**`restore_entries()`** — add `singers_json` to the INSERT column list so undo/redo round-trips the field.

### Route changes (`routes.py`)

**`/rotation/add`** — accepts optional `singers` array in the JSON body. If present, passes to `add_entry(singers=...)`. If absent, uses existing `singer` string behavior.

**`/rotation/edit`** — accepts optional `singers` array. Same logic.

**`_add_songs_sung()`** — for multi-singer entries (where `singers_json` is non-null), the songs-sung count shown on the entry is the **minimum** count across all singers in the group. This is the fairest representation: the person who has waited longest in the group determines the priority.

All other routes unchanged. Entry dicts automatically include `singers_json` via `_row_to_dict()`.

## Frontend Changes

### Pill input component (`app.js`)

The existing singer `<input>` gets wrapped in a container div that manages pills + text input:

**State:** `singerPills` array tracks confirmed singer names.

**Keydown handlers:**
- **Tab, comma, `&`** — if input has text, trim it, push to `singerPills`, render pill, clear input. `preventDefault()` so Tab does not move focus.
- **Backspace on empty input** — pop last pill from `singerPills`, re-render.
- **Enter** — move focus to song field (existing behavior). Any remaining text stays until submit.

**Submit (`addRotationEntry()`):**
- If input still has text, add it as final singer.
- Always POST with `singers: [...]` array (even for single singer: `singers: ["Sarah"]`).
- Backend prioritizes `singers` array when present; falls back to `singer` string only if `singers` is absent (for backward compat with direct API callers).

**Pill rendering in input:** each pill is a `<span>` with the singer name and an `x` button. Click `x` removes from `singerPills` and re-renders.

### Rotation row rendering (`renderRotation()`)

- If `entry.singers_json` is non-null and has 2+ names: render each name as a small pill (`<span class="rotation-singer-pill">`).
- If `entry.singers_json` is null or has one name: render as plain text (identical to today).

### Songs-sung pill colors (updated thresholds)

```
0 songs  → Green  "NEW"   (prioritize — hasn't sung)
1 song   → Yellow "×1"
2-4 songs → Orange "×2"–"×4"
5+ songs → Red    "×5+"   (had plenty of turns)
```

Color classes:
- `.pill-new` — green (`#2d8a4e`)
- `.pill-once` — yellow (`#f59e0b`)
- `.pill-few` — orange (`#d4720a`)
- `.pill-many` — red (`#e74c3c`)

### CSS additions (`style.css`)

- `.singer-input-container` — flex-wrap container for pills + input in the add form
- `.singer-pill` — pill styling in the input form (with `x` button)
- `.rotation-singer-pill` — small rounded pill for multi-singer display in queue rows
- Updated pill color classes (green = new, red = many)
